# Релиз и установка

Срез добавляет один процесс релиза: workflow, формулу Homebrew, манифест Scoop и команды установки. Бинарники, заметки и каналы установки сходятся на одном номере версии. Провод API остаётся в `devapi.md` и `authorization_code_flow.md`. Этот файл его не копирует и не меняет. Примерные секреты, ключи, токены и authorization code из контракта сюда не переносятся и в README, формулу, манифест, changelog, workflow и тесты не копируются.

crates.io не используется. В `Cargo.toml` уже стоит `publish = false`, и это закрыто.

README и `.github/workflows/ci.yml` в дереве уже есть. Этот срез их не строит заново. Workflow проверок не заменяется релизным.

Закрытые решения из тела задачи и `AGENTS.md` не переоткрываются. Ниже — поведение среза, публичный контракт и проверки, которые его показывают.

## Не входит

- Новая команда, флаг, код выхода, человеческий текст CLI, `--json`, auth, файл токенов, заголовок и разбор ответа.
- Вызов Boosty, в том числе из workflow, формулы и тестов.
- Тег, GitHub Release и запуск этого workflow. Срез только кладёт workflow и манифесты в дерево.
- Pull request, push ветки среза и токен, которого нет у `GITHUB_TOKEN` этого репозитория. PR в `microsoft/winget-pkgs` не открывается.
- Отдельный репозиторий `homebrew-*` и отдельный bucket-репозиторий.
- `cargo binstall`, публикация крейта и смена `publish = false`.
- Conventional Commits. Текущие сообщения им не следуют, и релиз их не требует.
- Переписывание старой истории changelog, перенос тега, force-push и amend.
- Бейдж CI и щиты. Срез оформления их не обещал, этот срез их не добавляет.

## Публичный контракт команд CLI

Контракт `boosty` не меняется. Он остаётся тем, что уже записан в `AGENTS.md`: `auth login`, `auth refresh`, `auth status`, `user`, `subscription-levels`, `subscriptions`, `subscribers` и глобальный `--json`. Флага версии нет: clap его не показывает. Формула и манифест не добавляют флаг и не вызывают Boosty, чтобы проверить бинарник.

Публичный контракт этого среза — команды установки в README. Они ставят один и тот же бинарник `boosty` одной и той же версии.

## Одна версия

Номер версии — поле `version` в `Cargo.toml`, как оно записано, без переписывания. На старте среза это `0.1.0`. Срез номер не поднимает и тег `v0.1.0` не создаёт.

Один и тот же номер виден в:

- `Cargo.toml`
- теге `v` + этот номер, когда тег позже кто-то поставит
- GitHub Release этого тега, когда workflow позже его создаст
- заголовке секции CHANGELOG, которую тот же workflow дописывает
- командах установки в README, формуле и манифесте Scoop

Тег обязан совпадать с `version` посимвольно после префикса `v`. `v0.1.0` подходит к `0.1.0`. `0.1.0` без `v`, `v0.1`, `v0.1.0-beta` и другой номер — нет. Workflow не нормализует номер и не читает версию из названия тега, если она расходится с `Cargo.toml` того коммита, на котором он запущен.

## Запуск

Релизный workflow — отдельный файл `.github/workflows/release.yml`. События, и только они:

- push тега, имя которого — `v` и три числовых компонента через точку
- `workflow_dispatch` без входных параметров

Push в `main`, pull request и любой другой ref релиз не создают. `workflow_dispatch` не вводит версию, секрет и токен. Он использует ref, с которого его запустили.

Перед сборкой и перед созданием Release job сравнивает имя ref с `v` + `version` из `Cargo.toml` этого ref. Сравнение видно в самом workflow-файле, не спрятано в стороннем action. Несовпадение, ref-ветка и ref без тега — job падает и не создаёт Release, не загружает архивы и не пишет CHANGELOG. Второй запуск по тегу, у которого Release уже есть, тоже падает и не перезаписывает Release и не переписывает уже записанную секцию changelog.

Права job — `contents: write`, чтобы позже создать Release и дописать changelog в `main`. Контекста `secrets` нет. Отдельный PAT, winget-токен и Boosty-креденшелы не задаются. Проверочный workflow это право не получает: его файл не меняется.

Checkout проверок остаётся с `persist-credentials: false`. Релизный checkout может сохранить credentials только потому, что job дописывает changelog. Это не повод менять checkout проверок.

## Архивы

Один job собирает бинарник `boosty` и кладёт в Release ровно пять архивов плюс контрольные суммы:

- `boosty-linux-x86_64.tar.gz` — внутри на корне архива файл `boosty`
- `boosty-linux-aarch64.tar.gz` — то же
- `boosty-macos-aarch64.tar.gz` — то же
- `boosty-macos-x86_64.tar.gz` — то же
- `boosty-windows-x86_64.zip` — на корне `boosty.exe`

Unix-бинарник в архиве исполняемый. Пять имён — пять разных целей. Один архив, выложенный под пятью именами, контракт не закрывает. Каталога внутри архива нет: формула и Scoop не угадывают `extract_dir`.

Рядом лежит `SHA256SUMS`: SHA-256 каждого из пяти архивов, строчная hex-сумма, по одной строке `сумма  имя`. Других архивов и других алгоритмов нет.

Сборка идёт со stable toolchain, которого хватает для edition 2024, как в workflow проверок. Числовой релиз Rust не фиксируется. Версия в бинарнике — версия крейта, без подмены. Любой из пяти срывов не даёт создать Release с неполным набором.

Чем собирать linux-aarch64 и macos-x86_64, workflow выбирает сам. Самохост и секрет для этого не требуются. Живой запуск в этом срезе не делается, поэтому проверка здесь — список пяти целей в workflow-файле, а не скачанный архив.

## Заметки

Текст заметок — subject коммитов с предыдущего тега вида `vX.Y.Z` и до текущего, без subject самого предыдущего тега. Предыдущий — ближайший такой тег в истории, не любой тег. Если предыдущего нет, берутся subject от корня истории до текущего тега включительно. Тела коммитов, хеши и ссылки на PR не добавляются. Subject не переписываются и не фильтруются по Conventional Commits.

Порядок один: от старых к новым. Тот же текст, байт в байт, становится телом GitHub Release и дописываемой секцией CHANGELOG. У тела Release нет подвала, которого нет в секции.

Секция начинается с заголовка `## X.Y.Z`, где `X.Y.Z` — номер из `Cargo.toml`, без префикса `v`. Дальше subject, каждый на своей строке. Пустой список subject — всё равно этот заголовок и ничего лишнего. Выдуманной фразы «нет изменений» нет.

`CHANGELOG.md` в этом срезе появляется без секции релиза. Заголовка `## 0.1.0` в нём нет: релиза ещё не было, и историю выдумывать нельзя. Короткий заголовок файла может сказать, что секции дописывает релиз и что старые секции не переписываются. Сам этот заголовок workflow потом не меняет.

Когда workflow позже публикует релиз, он дописывает секцию в конец файла и коммитит это в `main` обычным коммитом. Старые байты файла остаются префиксом. Тег не двигается. `Cargo.toml` `version` и `publish` этот коммит не меняет. Если на `main` номер уже другой, job падает и не переписывает формулу под чужой номер. Если секция `## X.Y.Z` уже есть, job падает и не правит её. Force-push, amend и pull request workflow не использует.

Коммит changelog не содержит токенов и секретов. Conventional Commits от него не требуются.

## Один шаблон URL

Три канала установки ссылаются на одну и ту же строку шаблона:

`https://github.com/kirich1409/boosty-cli/releases/download/v{version}/boosty-{target}.{ext}`

`{version}` — номер из `Cargo.toml`. `{target}` — одно из пяти имён выше без префикса `boosty-`. `{ext}` — `tar.gz`, а для `windows-x86_64` — `zip`.

Эта строка целиком лежит в README, в `Formula/boosty.rb` и в `bucket/boosty.json`. Конкретный URL архива в этих файлах — только подстановка в этот шаблон. Другого хоста, crates.io, bottle-url Homebrew и URL отдельного tap или bucket нет.

Каналы:

1. Homebrew — macOS и Linux, одна формула, четыре unix-архива из шаблона.
2. Scoop — Windows, один манифест, архив `windows-x86_64` из того же шаблона.
3. Раздел установки README — те же команды и та же строка шаблона.

`cargo install` — установка из исходников, не четвёртый URL релиза. На шаблон он не ссылается.

## Homebrew

macOS и Linux ставятся формулой из этого репозитория. Отдельный `homebrew-*` не создаётся.

Команда в README — ровно эти две строки, и другого `brew` в README нет:

```
brew tap kirich1409/boosty-cli https://github.com/kirich1409/boosty-cli
brew install kirich1409/boosty-cli/boosty
```

Одноаргументный `brew tap kirich1409/boosty-cli` выдумывает `github.com/kirich1409/homebrew-boosty-cli`. Этого tap нет и создавать его нельзя, поэтому такой команды в README нет. `brew install` по произвольному URL файла формулы текущий Homebrew не выполняет: загрузка формулы без checksum с URL не поддерживается. Двухаргументная форма tap как раз для репозитория без префикса `homebrew-`: URL указывает на это дерево, не на выдуманный tap.

Формула — `Formula/boosty.rb`. Каталога `HomebrewFormula` нет, `.rb` в корне нет. Имя формулы `boosty`. Она ставит готовый бинарник из архива релиза, а не собирает крейт и не ходит на crates.io.

Четыре URL выбираются блоками Homebrew `on_macos` / `on_linux` и `on_arm` / `on_intel`. Внутри `install` эти блоки не используются. На macOS arm — `macos-aarch64`, на macOS intel — `macos-x86_64`, на Linux arm — `linux-aarch64`, на Linux intel — `linux-x86_64`. Windows в формуле нет.

Лицензия формулы — `license any_of: ["MIT", "Apache-2.0"]`. Это та же двойная лицензия `MIT OR Apache-2.0`, не выбор одной. `homepage` — `https://github.com/kirich1409/boosty-cli`.

SHA-256 в формуле обязателен для реальной установки, но в этом срезе его нет: архива ещё нет, сумму выдумывать нельзя. Позже workflow пишет в формулу суммы из `SHA256SUMS` того релиза, который сам собрал, и коммитит это вместе с changelog. До этого в формуле нет 64-значной hex-суммы.

Живой `brew install` этот срез не запускает. Проверка команды — что она указывает на формулу в этом дереве, а не на отдельный tap.

## Scoop

Windows ставится манифестом из этого репозитория. Отдельный bucket не создаётся. PR в winget нет.

Команда в README:

```
scoop install https://raw.githubusercontent.com/kirich1409/boosty-cli/main/bucket/boosty.json
```

Это установка манифеста по URL, как в справке `scoop install`. `scoop bucket add` в README нет.

Файл — `bucket/boosty.json`. Поля: `version` равен номеру из `Cargo.toml`, `url` — windows-архив из шаблона для этого номера, `bin` — `boosty.exe`, `license` — `MIT|Apache-2.0`. Архитектура только 64-bit: других windows-архивов job не собирает. `hash` в этом срезе нет, по той же причине, что нет `sha256` в формуле. Workflow дописывает SHA-256 из `SHA256SUMS`. Префикса `sha1:` и `md5:` нет.

## README

Раздел установки на русском. В нём видны номер из `Cargo.toml`, тег `v` + этот номер, строка шаблона и три команды: две строки Homebrew, одна команда Scoop и:

```
cargo install --git https://github.com/kirich1409/boosty-cli
```

`cargo install` остаётся установкой из исходников. Флага `--tag` у этой команды нет: задача задала команду без него. Рядом написано, что `cargo binstall` и crates.io не обещаны, потому что `publish = false`.

Старые разделы README не переписываются и не теряют уже обещанные команды и переменные. Значения переменных по-прежнему не задаются. Полный текст лицензии в README не копируется.

Тест `readme_has_no_install_channel_or_ci_badge` запрещал `brew`, `scoop`, `cargo install` и `GitHub Releases`. Для этого среза этот запрет снят только на команды и шаблон выше. Запрет на `crates.io`, `cargo binstall`, бейдж, `shields.io`, `homebrew-`, `winget`, `bucket add` и на текст лицензии остаётся.

## AGENTS.md

В `AGENTS.md` добавляется только правило релиза: тег `vX.Y.Z` совпадает с `version` в `Cargo.toml`, crates.io выключен, установка идёт из этого репозитория, а не из отдельного tap. Других правок этого файла срез не делает. Changelog, версии зависимостей и пересказ workflow туда не переносятся.

## Лицензия и publish

`LICENSE-MIT`, `LICENSE-APACHE` и `license = "MIT OR Apache-2.0"` уже в дереве. Copyright holder — `kirich1409`. Срез файлы лицензии не переписывает и другую лицензию не выбирает. `publish = false` не меняется. `cargo publish` в workflow нет.

## Workflow проверок

`.github/workflows/ci.yml` не меняется. Он по-прежнему единственный workflow проверок: push и pull request в `main`, три команды `cargo` из `AGENTS.md`, без релиза, без артефакта бинарника и без `secrets`. Релизный файл его не подменяет и не включает в себя эти проверки как замену.

## Проверки

Локально, из корня репозитория, зелёные:

- `cargo fmt --check`
- `cargo clippy --all-targets --all-features -- -D warnings`
- `cargo test`

`cargo test` не ходит в сеть, не вызывает Boosty, Homebrew, Scoop и GitHub и не читает `BOOSTY_API_KEY`, `BOOSTY_CLIENT_SECRET` и файл токенов разработчика. Сам workflow не запускается. Зелёный прогон на GitHub недоступен, пока другая сессия не запушит. Его отсутствие не заменяет чтение файлов.

Тесты читают дерево и показывают:

- `.github/workflows/ci.yml` не изменён; `.github/workflows/release.yml` — второй файл, и он не заменяет проверки
- события релиза — только push тега `vX.Y.Z` и `workflow_dispatch` без inputs; push в `main` релиз не создаёт
- в workflow видно сравнение тега с `v` + `version` из `Cargo.toml` и отказ до создания Release
- пять имён архивов, `SHA256SUMS` и отсутствие `cargo publish`, `secrets`, winget и вызова Boosty
- строка шаблона есть в README, `Formula/boosty.rb` и `bucket/boosty.json`; конкретные URL архивов — только её подстановки для номера из `Cargo.toml`
- команды README — двухаргументный tap этого URL, `brew install kirich1409/boosty-cli/boosty`, scoop по raw URL манифеста из `bucket/boosty.json` и точный `cargo install --git https://github.com/kirich1409/boosty-cli`
- нет `homebrew-`, одноаргументного tap, `scoop bucket add`, `winget`, `crates.io`, `cargo binstall` и `publish = true`
- формула указывает `license any_of: ["MIT", "Apache-2.0"]`; манифест — `MIT|Apache-2.0`; версия манифеста равна `Cargo.toml`
- в формуле и манифесте нет выдуманной 64-значной hex-суммы
- `CHANGELOG.md` есть и не содержит секцию `## 0.1.0`; workflow дописывает `##` + номер, а не переписывает старые секции
- `AGENTS.md` содержит правило релиза и не теряет уже записанный контракт команд
