# Уровни и подписки

Срез добавляет два чтения относительно блога приложения: `boosty subscription-levels` и `boosty subscriptions`. Провод ответов остаётся в `devapi.md`. Этот файл его не копирует и не меняет. Примерные секреты, ключи, токены и тела из контракта сюда не переносятся и в код, тесты и фикстуры не копируются.

Каркас уже есть: клиент, вывод, конфиг, `auth` и `user`. Срез их не заменяет и второй HTTP-слой не строит. Команды не собирают URL и не ставят заголовок авторизации сами: это делает уже существующий клиент. Общая точка вывода — уже существующий вывод. Её можно расширить для этих команд. Уже обещанный текст `auth login`, `auth refresh`, `auth status` и `user` не меняется.

Закрытые решения из тела задачи и `AGENTS.md` не переоткрываются. Вызовы по API key относятся к блогу приложения. Имени блога и blog id нет и не добавляются, чтобы команды не стали похожи на веб-API.

## Не входит

- `subscribers` и его query: `is_free`, `limit`, `offset`, `extra.nextOffset`. Строка `следующее смещение` этим командам не принадлежит: в их ответах этого поля нет, и срез его не выдумывает.
- Смена поведения `auth login`, `auth refresh`, `auth status` и `user`, включая refresh, файл токенов и Bearer на `/v1/user`.
- Имя или id блога, пагинация, второй запрос, обход страниц, фильтр `isDeleted` и любой флаг такого фильтра.
- Заголовок `Authorization`, в том числе Bearer и Basic, на этих двух вызовах. Режимы не подменяются и оба семейства заголовков не отправляются.
- Веб-API Boosty и модели крейта `boosty_api`: там `price` — число, удаление — `deleted`, уровни обёрнуты в `data`. Эти модели не использовать.
- MCP, library crate, agent skill, pull request и мерж в main.
- Новые поля ответа, query и grant, которых нет в `devapi.md` для этих двух методов.

## Команды

- `boosty subscription-levels`
- `boosty subscriptions`

Позиционных аргументов нет. Своих флагов у команд нет. API key, client secret, access token и refresh token не принимаются флагами и позиционными аргументами. Имя блога, blog id, `is_free`, `limit` и `offset` тоже не принимаются.

Глобальный `--json` принимается и до, и после подкоманды: `boosty --json subscription-levels` и `boosty subscription-levels --json`, так же для `subscriptions`.

Лишний аргумент или неизвестный флаг — usage, код 2. Stdout пуст. С `--json` stderr — один объект `{"error","kind"}` с `kind` равным `usage`, без английского текста clap. Код 2 остаётся у clap.

Справка, описание команд и флагов — русские. Английский шаблон help clap не оставлять.

Один запуск — один запрос к DevAPI, и только если до него дошло. `subscriptions` не вызывает `/v1/subscription_levels`, и наоборот. Уровни во втором ответе уже вложены.

## Запрос

Обе команды — `GET` к базе DevAPI. База по умолчанию `https://devapi.boosty.to/v1`; в тестах её подменяет уже существующий `BOOSTY_DEVAPI_BASE`. Другого хоста нет.

- `subscription-levels`: путь `/v1/subscription_levels`
- `subscriptions`: путь `/v1/subscriptions`

Query нет. В пути нет имени блога и blog id.

Ключ читается из `BOOSTY_API_KEY` тем же правилом непустого значения, что и остальные переменные окружения. Флага для ключа нет. Нет переменной или она пустая — это отсутствующие учётные данные, код 3. Запрос не уходит. Пустой `X-Api-Key` не отправляется. Файл токенов, client id и client secret для этого не нужны и не подставляются. Команды не читают и не переписывают файл токенов и не вызывают token endpoint. Неразрешённый путь к файлу токенов и отсутствие домашнего каталога сами по себе эти команды не валят, если ключ есть: это не bearer-вызовы.

Заголовок авторизации ровно один: `X-Api-Key`. Значение — сам ключ, без схемы и без префикса `Bearer`. `Authorization` нет, даже если файл токенов есть и даже если заданы клиентские учётные данные. Оба заголовка не отправляются.

Неуспех DevAPI, включая HTTP 401 и 403, не повод подставить Bearer, обновить токен или повторить запрос. Это сбой API, код 4.

Исходящий HTTP, как и остальные вызовы, ставит `Accept: application/json`, таймаут 30 секунд и user agent `boosty-cli/<version>`. Это не второй заголовок авторизации.

Негодный `BOOSTY_DEVAPI_BASE` остаётся уже существующей локальной ошибкой клиента, код 5, без запроса. Срез этот код не переназначает.

## Разбор

Ответ разбирается как JSON, даже если content type нет. Неизвестные поля игнорируются. Нет поля, которое формат ответа в `devapi.md` задаёт для этого метода, или оно не того типа — ошибка, DevAPI повторно не вызывается. Приведения типов нет: строка вместо числа или логического значения не становится числом, число вместо строки не становится `price` или `payments`.

`subscription-levels` требует массив `subscriptionLevels`. `subscriptions` требует оба массива: `subscriptions` и `subscriptionLevels`. Пустой массив — успех, не отсутствие поля. `null` вместо массива — ошибка типа.

Объект уровня, обязательные имена без добавления и без переименования: `id`, `price`, `authorId`, `name`, `createTime`, `isDeleted`. `id`, `authorId` и `createTime` — целые `i64`, не `i32`. `price` и `name` — строки. `isDeleted` — JSON-логическое значение.

Объект подписки: `id`, `ownerId`, `levelId`, `startTime`, `endTime`, `nextPayTime`, `subscriberId`, `payments`. Все id и timestamps — `i64`, не `i32`. `payments` — строка.

`endTime` и `nextPayTime`, равные `0`, — обычные целые, не ошибка разбора. То же для нуля в `createTime` и `startTime`. Ноль не становится JSON `null` и не становится `1970-01-01`.

Строка с `isDeleted: true` остаётся в массиве. Срез её не фильтрует и не выкидывает ни одну другую документированную строку. Уровень, на который нет ссылки из подписки, остаётся. Подписка, чей `levelId` нет среди уровней, тоже остаётся. Срез не синтезирует недостающий уровень и не соединяет списки сам.

Неуспех HTTP, обрыв, таймаут, не-JSON и отсутствие обязательного поля — код 4. Stdout пуст. Тело ответа в stderr, логи, `Display` и `Debug` не попадает. Ключ не попадает ни в один поток, ни в логи, ни в `Display`, ни в `Debug`.

## Человеческий вид

Без `--json` stdout — русский текст, не дамп JSON и не колонка сырых имён полей. Конкретные русские подписи сверх «удалён» и «нет» не фиксируются.

Вид уровня один на оба ответа. Один и тот же объект уровня даёт один и тот же блок и в `subscription-levels`, и во вложенном `subscriptionLevels` у `subscriptions`: то же имя, тот же id, та же цена, то же время, та же пометка удаления. Второго макета нет.

Блок уровня группирует свои поля. Имя раньше id. Цена, время создания и пометка удаления остаются в этом блоке.

Блок подписки группирует свои поля: id и времена остаются вместе, не колонкой сырых имён. В ответе подписок вложенные уровни печатаются тем же блоком уровня, своей группой, а не размазанными по колонкам подписки. Срез не требует склеивать подписку с уровнем по `levelId`.

`price` в модели и в `--json` остаётся строкой как в ответе. В человеческом виде она не разбирается как число: сумма не округляется, хвост нулей не отрезается, знак валюты не подменяется. Строку из буквенного префикса сразу и суммы, как `RUB11.00`, можно показать как `11.00 RUB`: те же символы префикса и суммы, один пробел между ними. Иная строка показывается как пришла. `payments` этой перестановкой не трогать. Поскольку вид уровня один, одна и та же строка `price` выглядит одинаково в обеих командах.

Ненулевой timestamp в человеческом виде — локальные дата и время. Ноль — слово «нет», не `1970-01-01`, не JSON `null` и не дефис. Это относится к `createTime`, `startTime`, `endTime` и `nextPayTime`. Правило не переписывает срок сессии в выводе auth.

`isDeleted: true` в человеческом виде помечается «удалён». `false` остаётся в выводе и не помечается «удалён». Ключ `isDeleted` не печатается.

Пустой список — успех, код 0. Это не ошибка и не повод оставить stdout пустым: пустой stdout значит ошибку.

## Вывод

Успех — код 0. На успехе stderr пуст.

С `--json` stdout — тело ответа с именами полей спеки, один JSON-объект, без второй строки и без логов. Неизвестного поля из ответа в нём нет. Порядка ключей нет в контракте. `price` и `payments` — те же строки, что в ответе. Ноль остаётся целым `0`. `isDeleted: true` остаётся логическим `true`. Пустые массивы остаются пустыми массивами.

На любой ошибке stdout пуст. С `--json` на stderr ровно один объект `{"error","kind"}`. Текст `error` английский. `kind` — ровно одно из `usage`, `auth`, `api`, `io`. Без `--json` на stderr короткое русское сообщение. Ключ, токены и секреты не печатаются.

Коды:

- `0` — успех, включая пустые списки и строки с `isDeleted: true`
- `2` — usage
- `3` — нет или пустой `BOOSTY_API_KEY`
- `4` — сбой, неуспешный HTTP или негодное тело DevAPI
- `5` — негодный базовый URL, как у существующего клиента

Соответствие `kind`: `usage` — 2, `auth` — 3, `api` — 4, `io` — 5.

## Проверки

Тесты ходят только на локальный сервер через уже существующую подмену базы. Boosty не вызывается. `BOOSTY_API_KEY`, `BOOSTY_CLIENT_SECRET` и файл токенов разработчика из окружения не читаются. Свои фейковые значения тесты задают сами. Фикстуры лежат в `tests/fixtures/`, отдельные тела для обоих ответов. Значения фейковые и не скопированы из примеров контракта. Образец ключа из `devapi.md` в фикстуры, код и этот файл не попадает.

- Разбор фикстуры уровней: обязательные поля на месте, неизвестное поле отброшено, `isDeleted: true` остаётся в списке, `id` или timestamp вне диапазона `i32` остаётся `i64`, `price` остаётся строкой. Нет обязательного поля, `price` числом или `isDeleted` не логическим значением — ошибка. Пустой `subscriptionLevels` разбирается успешно.
- Разбор фикстуры подписок: оба массива обязательны, в уровнях есть `isDeleted: true`, `endTime` и `nextPayTime` равны `0` и остаются `i64`, не ошибка и не `null`. `payments` остаётся строкой. Хотя бы один id вне диапазона `i32` остаётся `i64`. Пустые оба массива — успех. Нет одного из массивов — ошибка.
- Локальный HTTP, отдельно на каждую команду: ушёл один `GET`, путь своей команды, query нет, в пути нет блога. Ровно один заголовок `X-Api-Key`, значение — фейковый ключ теста, без схемы. `Authorization` нет, Bearer нет, Basic нет, даже если тесту заданы свой файл токенов и свой клиентский секрет. Второго запроса нет: `subscriptions` не ходит на `/v1/subscription_levels`. `Accept: application/json` и user agent `boosty-cli/<version>` есть.
- Нет или пустой `BOOSTY_API_KEY`: код 3, сеть молчит, stdout пуст, даже если файл токенов на месте. Token endpoint не вызывался. Файл токенов не переписан.
- `--json` до и после подкоманды. Stdout парсится как один JSON-объект с именами полей спеки, без лишнего поля фикстуры и без второй строки. `price` и `payments` посимвольно равны ответу. Ноль остаётся целым `0`, не `null` и не строкой даты. `isDeleted: true` на месте. Ключа в stdout и stderr нет.
- Человеческий stdout: это не JSON и не ключи `isDeleted`, `createTime`, `endTime`, `nextPayTime`, `price`. Имя уровня раньше его id. Строка с `isDeleted: true` содержит «удалён» и не выкинута. Ноль показан как «нет», без `1970-01-01`. Ненулевой timestamp при фиксированной временной зоне — локальные дата и время. Буквы валюты и символы суммы на месте, сумма не округлена. Если `RUB11.00` показан как `11.00 RUB`, тот же уровень во второй команде показан так же. `payments` не переставлен как валюта.
- Один и тот же объект уровня даёт один и тот же человеческий блок в обеих командах.
- Пустой список: код 0, stdout не пуст. С `--json` это тело с пустым массивом, не объект ошибки.
- Ошибка DevAPI и тело без обязательного поля: stdout пуст, код 4, второго запроса нет. С `--json` stderr парсится как `{"error","kind"}`.
- Лишний позиционный аргумент, флаг блога или флаг `is_free` — usage, код 2, сеть молчит.
- Help обеих команд на русском и это не английский шаблон clap.
- Уже обещанный человеческий и JSON-вывод `user` и срок в выводе auth не меняются из-за правила «нет» для нулевого timestamp этих команд.
