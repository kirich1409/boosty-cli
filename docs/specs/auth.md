# Вход и обновление токена

Срез закрывает вход по `authorization_code_flow.md` и каркас бинарника `boosty`, без которого эти команды не собрать. Провод API остаётся в `authorization_code_flow.md` и `devapi.md`. Этот файл его не копирует и не меняет. Примерные секреты, токены и authorization code из контракта сюда не переносятся и в код, тесты и фикстуры не копируются.

Закрытые решения из тела задачи и `AGENTS.md` не переоткрываются. Ниже — поведение среза, публичный контракт команд и проверки, которые его показывают.

## Не входит

- Команды `user`, `subscription-levels`, `subscriptions`, `subscribers` и любой вызов DevAPI.
- Заголовок `X-Api-Key`, веб-API Boosty, MCP, library crate, agent skill.
- Автообновление за 60 секунд до bearer-вызова. В этом срезе нет команды, которая шлёт Bearer.
- Новые query- или form-параметры, grant и поля ответа, которых нет в `authorization_code_flow.md`. В том числе PKCE и `scope`.
- Pull request и мерж в main.

## Команды

Бинарник — `boosty`. В этом срезе только:

- `boosty auth login`
- `boosty auth refresh`
- `boosty auth status`

У команд нет позиционных аргументов. API key, client secret, access token и refresh token не принимаются флагами и позиционными аргументами. Других флагов, кроме глобального `--json`, нет.

`--json` глобальный и принимается и до, и после подкоманды: `boosty --json auth …` и `boosty auth … --json`.

`auth login` — единственная интерактивная команда. Агенты её не запускают, чтобы получить данные: у этого среза нет команды чтения DevAPI.

## Окружение и файл токенов

Хосты по умолчанию живут в клиенте, не в вызывающем коде:

- authorize: `https://boosty.to/app/oauth2/authorize`
- token: `https://api.boosty.to/oauth/server/token`
- DevAPI: `https://devapi.boosty.to/v1`

`BOOSTY_AUTHORIZE_URL`, `BOOSTY_TOKEN_URL` и `BOOSTY_DEVAPI_BASE` — только подмена для тестов и локальных заглушек. Этот срез на DevAPI ничего не отправляет.

`BOOSTY_CLIENT_ID` и `BOOSTY_CLIENT_SECRET` не хранятся в файле токенов и не принимаются флагами. Секрет нужен только чтобы собрать `Authorization: Basic`. `BOOSTY_CLIENT_ID` — тот же идентификатор, который `authorization_code_flow.md` уже требует как query `client_id` на authorize и как левую часть Basic. Нового параметра это не добавляет.

`BOOSTY_REDIRECT_URL` — зарегистрированный URL. Один и тот же текст уходит как `redirect_url` на authorize и как `redirect_uri` на обмен кода. Имена разные намеренно. Комментарий у вызова token-запроса это фиксирует. Значение совпадает с регистрацией посимвольно; query-кодирование authorize не меняет текст.

Путь файла токенов: `$XDG_CONFIG_HOME/boosty-cli/tokens.json`, иначе `~/.config/boosty-cli/tokens.json`, в том числе на macOS. Не Application Support. Подмена — `BOOSTY_TOKEN_PATH`.

Файл — JSON и хранит только `access_token`, `refresh_token`, `token_type` и абсолютный `expires_at` в unix-секундах. `expires_at` считается при записи как время записи плюс `expires_in`. `expires_in` в файле не хранится. Client secret и API key в файле не хранятся. Чужие поля при чтении игнорируются. Нет обязательного поля или JSON не читается — это локальная ошибка файла, код 5; файл не переписывается. Каталог, который создаёт команда, получает режим `0700`. Файл после записи — `0600`.

Запись только после полного успешного ответа token endpoint: временный файл в том же каталоге и rename. Сообщение об успехе — после успешного rename. Ошибка обмена, refresh или rename оставляет прежний файл нетронутым. Новые токены не остаются по конечному пути. Это относится и к первому `login`, и к повторному `login`, и к `refresh`.

## `auth login`

На каждую попытку — новый криптографический `state`. Слушатель принимает callback только на host, port и path из `BOOSTY_REDIRECT_URL`. Адрес не хардкодится, в том числе не подставляется `127.0.0.1` вместо host из URL. Не-loopback не биндится. Loopback — адрес loopback или имя `localhost`, если так записано в URL. Другой порт не выбирается. Локальный TLS и второй порт не поднимаются.

Если URL не разбирается, host не loopback, порта в URL нет или схема не `http`, это локальная конфигурация: код 5, слушатель не стартует, браузер не открывается, token endpoint не вызывается.

Если нет `BOOSTY_CLIENT_ID` или `BOOSTY_CLIENT_SECRET`, это отсутствующие учётные данные: код 3, без слушателя и без token endpoint.

Иначе слушатель стартует, затем открывается системный браузер на authorize URL. Если браузер не открылся, URL печатается на stderr, и ожидание callback продолжается. Само по себе это не ошибка входа. URL на stdout не печатается.

Authorize URL содержит только параметры из контракта: `client_id`, `redirect_url`, `response_type=code`, `state`. Имени `redirect_uri` на authorize нет. Секрета в URL нет.

Ожидание callback — не дольше 3 минут. Таймаут — отказ авторизации, код 3, не локальная ошибка. Token endpoint не вызывается. После первого callback на нужном path или по таймауту слушатель останавливается. Запрос на другой path не считается callback.

Дальше:

- `error` или `error_reason`, даже вместе с `code` и даже если второго поля отказа нет: код 3, token endpoint не вызывается.
- `state` нет или он не равен `state` этой попытки: код 3, token endpoint не вызывается.
- Согласие — только совпавший `state`, непустой `code` и ни `error`, ни `error_reason`. Иначе код 3 и token endpoint не вызывается.

Ответ браузеру короткий, на русском, и не содержит authorization code, токенов и секретов.

Обмен кода: `POST` на token URL, тело `application/x-www-form-urlencoded`, не query. Заголовок авторизации ровно один: `Authorization: Basic`. Basic — стандартный base64, с padding, от `client_id + ":" + secret`. Не base64url. Form-поля обмена ровно те, что контракт задаёт для `grant_type=authorization_code`: `grant_type`, `redirect_uri`, `code`. Имени `redirect_url` в form нет. Секрет в body не кладётся.

Успешный разбор ответа требует поля, которые контракт задаёт для ответа token endpoint: `access_token`, `expires_in`, `token_type`, `refresh_token`. Неизвестные поля ответа игнорируются. Иначе файл токенов не меняется, а код берётся из правила ниже. `token_type` сохраняется как пришёл. Контракт не требует отказывать из-за другого `token_type`; этот срез такой отказ не добавляет и Bearer ни на один хост не шлёт.

## `auth refresh`

Ручной refresh не смотрит на срок и не применяет окно 60 секунд. Нет файла токенов или в нём нет `refresh_token` — код 3, token endpoint не вызывается, файл не создаётся.

Иначе `POST` на тот же token URL, тот же Basic и то же ограничение «ровно один» заголовок авторизации. Form-поля ровно те, что контракт задаёт для refresh: `grant_type=refresh_token` и текущий `refresh_token`. `redirect_uri`, `code` и секрет в body не отправляются.

Успех приносит новый refresh token в теле ответа. Оба новых токена, `token_type` и новый `expires_at` пишутся атомарно до сообщения об успехе. В файл пишется `refresh_token` из ответа, и после успеха прежний refresh token не остаётся текущим. Сообщение об успехе — тот же срок и путь, что у `login` и `status`, без значений токенов: отдельной формы вывода у refresh нет.

Если token endpoint не выдал токены, файл не меняется и успех не печатается. Код — по правилу ниже. Ошибка rename — код 5, прежний файл не меняется.

## `auth status`

Читает локальный файл токенов и ничего не отправляет на token endpoint и DevAPI. Успех печатает срок и путь к файлу, не значения токенов. Нет файла — код 3. Файл не читается или в нём нет обязательного поля — код 5, файл не переписывается.

## Вывод и коды

На успехе `login`, `refresh` и `status` не печатают значения токенов, секрет и authorization code.

Без `--json` человеческий stdout — короткий русский текст, не дамп JSON и не колонка сырых имён полей. В нём есть путь к файлу токенов и срок как локальные дата и время. `--json` в этом тексте не смешивается.

С `--json` успешный stdout — один JSON-объект, без второй строки. Поля объекта: `expires_at` (целое, абсолютные unix-секунды, то же значение, что в файле) и `path` (путь к файлу токенов). Порядка ключей нет в контракте. Это поля stdout CLI, не поля DevAPI и не поля ответа token endpoint. Токенов, секрета и authorization code в объекте нет. На успехе stderr пуст, кроме одного случая: `login` не открыл браузер и печатает authorize URL на stderr.

При любой ошибке stdout пуст. С `--json` на stderr ровно один объект `{"error","kind"}`. Текст `error` английский. `kind` — ровно одно из `usage`, `auth`, `api`, `io`. Без `--json` на stderr короткое русское сообщение. Ни один поток не содержит токенов, секретов и authorization code. Полные тела ответов и authorization code не попадают в логи, `Display` и `Debug`.

Help, описания команд и флагов — русские. Английский шаблон help clap не оставлять.

Коды выхода:

- `0` — успех
- `2` — usage; код остаётся у clap
- `3` — auth: нет или отвергнуты учётные данные, отказ пользователя, чужой или пустой `state`, нет кода, таймаут входа, неудачный refresh
- `4` — API или транспорт: запрос не дошёл, таймаут, ответ не JSON, нет обязательного поля, HTTP 5xx
- `5` — локальная конфигурация или файловая ошибка, включая rename и негодный `BOOSTY_REDIRECT_URL`

Отказ token endpoint выдать токены при HTTP 4xx — это auth, код 3, а не транспорт. Успешное тело — только JSON с обязательными полями. Иное тело токены не записывает.

Соответствие `kind`: `usage` — 2, `auth` — 3, `api` — 4, `io` — 5. С `--json` usage тоже один JSON-объект `kind=usage` и код 2, без дополнительного английского текста clap на stderr.

Исходящий HTTP к token endpoint ставит `Accept: application/json`, таймаут 30 секунд и user agent `boosty-cli/<version>`. Версия — версия крейта. TLS — reqwest с rustls, без native-tls и OpenSSL. Один tokio runtime на краю процесса. `reqwest::blocking` из этого runtime не вызывается.

## Проверки

`cargo test` идёт без сети и без Boosty. Тесты не читают `BOOSTY_API_KEY`, `BOOSTY_CLIENT_SECRET` и файл токенов разработчика и проходят, когда их нет. Свои фейковые значения тесты задают сами. Образцы из `authorization_code_flow.md` и `devapi.md` в фикстуры не попадают. Token URL и authorize URL в тестах указывают на локальный сервер через подмену.

Проверки среза:

- Разбор фикстуры ответа token endpoint с фейковыми значениями. Обязательные поля контракта есть, чужое поле не мешает, отсутствие обязательного поля — ошибка. `expires_at` в записи равен unix-секундам времени записи плюс `expires_in`. Часы в тесте подменяются, ожидание трёх минут и сон до реального срока не нужны.
- Локальный HTTP-тест обмена и отдельно refresh: метод `POST`, path token endpoint, form-поля из контракта для этого grant и ни одного лишнего, тело не query, ровно один `Authorization: Basic`, нет `X-Api-Key` и нет Bearer. Тот же тест видит `Accept: application/json` и user agent `boosty-cli/<version>`.
- Кодирование Basic: стандартный base64 от `client_id + ":" + secret`, не из образцов контракта.
- На authorize есть `redirect_url` и нет имени `redirect_uri`. На обмене есть `redirect_uri` и нет имени `redirect_url`. Текст URL после декодирования один и тот же.
- Ротация refresh: после успеха в файле refresh token из ответа, не прежний; оба новых токена и `token_type` записаны; успех напечатан только когда конечный файл уже заменён.
- Чужой `state`: код 3, пустой stdout, token endpoint не вызывался, прежний файл не изменился. Ответ слушателя не содержит authorization code и токены.
- Отказ пользователя: `error` и `error_reason`, а также случай только одного из этих полей. Код 3, token endpoint не вызывался. Ответ слушателя не содержит authorization code и токены.
- Атомарная замена: неудачный refresh и неудачный rename оставляют прежние байты файла, stdout пуст, успеха нет. Успешная запись создаёт файл режимом `0600`, а создаваемый каталог — `0700`.
- Не-loopback и URL без порта или не `http`: код 5, bind нет, token endpoint не вызывался.
- Таймаут входа классифицируется как auth, код 3, без вызова token endpoint. Тест не спит три минуты.
- `--json` до и после подкоманды. На ошибке stdout пуст, на stderr один объект с английским `error` и нужным `kind`. На успехе объект содержит `expires_at` и `path` и не содержит токен, секрет и authorization code. Без `--json` stdout — не JSON, путь есть, значений токенов нет.
- Help на русском и это не английский шаблон clap. Разбор команд не принимает позиционные аргументы и флаг с секретом: лишнее — usage, код 2.
- `status` и неудачный `refresh` без файла не обращаются к сети.
- Отказ token endpoint с HTTP 4xx на обмен или refresh: код 3, файл не меняется. Обрыв, не-JSON или ответ без обязательного поля: код 4, файл не меняется.

После кода те же команды, что в `AGENTS.md`: `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test`.
