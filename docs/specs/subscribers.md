# Страница подписчиков

Срез добавляет `boosty subscribers`: один вызов `GET /v1/subscribers`. Провод ответа и query остаётся в `devapi.md`. Этот файл его не копирует и не меняет. Примерные секреты, ключи, токены и тела из контракта сюда не переносятся и в код, тесты и фикстуры не копируются.

Каркас уже есть: клиент с `X-Api-Key`, вывод, конфиг, `auth`, `user`, `subscription-levels` и `subscriptions`. Срез их не заменяет и второй HTTP-слой не строит. Команда не собирает URL и не ставит заголовок авторизации сама: это делает уже существующий клиент. Его можно расширить только так, чтобы этот путь получил query. Общая точка вывода — уже существующий вывод. Уже обещанный текст `auth`, `user`, `subscription-levels` и `subscriptions` не меняется.

Закрытые решения из тела задачи и `AGENTS.md` не переоткрываются. Вызов по API key относится к блогу приложения. Имени блога и blog id нет и не добавляются.

## Не входит

- Второй запрос и обход страниц внутри команды. Возвращённый `extra.nextOffset` не становится `offset` следующего запроса в том же запуске.
- Синтез `extra.nextOffset`, в том числе как `offset + limit`. Конец списка спека не задаёт, и команда его не выдумывает. Короткая страница, отсутствие поля и `nextOffset`, равный посланному `offset`, концом не считаются, и из-за этого вывод не глушится.
- Флаг фильтра `isDeleted`. Локальная отбраковка строк ответа, в том числе по `is_free` после получения тела. Параметр `is_free`, если флаг передан, только уходит в query.
- Смена смысла `subscription-levels` и `subscriptions`: путь, отсутствие query, заголовок, человеческий вид и JSON. Строка `следующее смещение` этим командам по-прежнему не принадлежит.
- Заголовок `Authorization`, включая Bearer и Basic. Подстановка Bearer, если ключа нет. Оба заголовка сразу.
- Имя или id блога. API key, client secret, access token и refresh token флагами или позиционными аргументами.
- Поля, которых формат `/v1/subscribers` в `devapi.md` не задаёт. В том числе `subscriptionLevels`, `price` и `isDeleted`. Скачивание `avatarUrl` отдельным запросом.
- Веб-API Boosty и модели крейта `boosty_api`. MCP, library crate, agent skill, pull request и мерж в main.
- Новые переменные окружения, новые поля ответа и умолчания `limit` или `offset`, которых нет в спеке.

## Команда

`boosty subscribers [--is-free true|false] [--limit N] [--offset N]`

Позиционных аргументов нет. Свои флаги только эти три, все опциональны. API key, client secret, access token и refresh token не принимаются.

`--is-free` принимает ровно строки `true` и `false`. Другое значение, другой регистр, `1`, `0` или флаг без значения — usage, код 2. Запроса нет.

`--limit` и `--offset` принимают целое той же ширины, что остальные целые DevAPI в этом крейте: `i64`, не `i32`. Иначе возвращённый курсор шире `i32` нельзя передать следующим `--offset` без изменения. Нецелое — usage, код 2, запроса нет. Команда не добавляет диапазон, которого нет в спеке: переданный ноль и отрицательное целое не выкидываются как «не задано» и не подменяются.

Глобальный `--json` принимается и до, и после подкоманды: `boosty --json subscribers` и `boosty subscribers --json`.

Лишний аргумент или неизвестный флаг, включая имя блога, blog id и фильтр `isDeleted`, — usage, код 2. Stdout пуст. С `--json` stderr — один объект `{"error","kind"}` с `kind` равным `usage`, без английского текста clap. Код 2 остаётся у clap.

Справка, описание команды и флагов — русские. Английский шаблон help clap не оставлять.

Один запуск — один запрос к DevAPI, и только если до него дошло. Вызывающий сам передаёт возвращённый `nextOffset` следующим `--offset`.

## Запрос

Метод `GET`. Путь — `/v1/subscribers` у базы DevAPI. База по умолчанию `https://devapi.boosty.to/v1`; в тестах её подменяет уже существующий `BOOSTY_DEVAPI_BASE`. В пути нет имени блога и blog id. Другого хоста и другого пути нет.

Query несёт ровно переданные флаги и ничего больше. Имена параметров: `is_free`, `limit`, `offset`. Порядок не входит в контракт.

- Без `--is-free` параметра `is_free` нет, в том числе когда переданы `limit` и `offset`. Пустое значение не шлётся.
- `--is-free true` даёт значение `true`. `--is-free false` даёт значение `false`. Не `1` и не `0`.
- Без `--limit` параметра `limit` нет. Без `--offset` параметра `offset` нет. Умолчания, которых нет в спеке, не подставляются.
- Переданный `--offset 0` или `--limit 0` уходит как `0`, а не опускается.

Ключ читается из `BOOSTY_API_KEY` тем же правилом непустого значения, что и остальные вызовы с API key. Флага для ключа нет. Нет переменной или она пустая — это отсутствующие учётные данные, код 3. Запрос не уходит. Пустой `X-Api-Key` не отправляется. Файл токенов, client id и client secret для этого не нужны и не подставляются. Команда не читает и не переписывает файл токенов и не вызывает token endpoint. Неразрешённый путь к файлу токенов и отсутствие домашнего каталога сами по себе эту команду не валят, если ключ есть: это не bearer-вызов.

Заголовок авторизации ровно один: `X-Api-Key`. Значение — сам ключ, без схемы и без префикса `Bearer`. `Authorization` нет, даже если файл токенов есть и даже если заданы клиентские учётные данные. Оба заголовка не отправляются.

Неуспех DevAPI, включая HTTP 401 и 403, не повод подставить Bearer, обновить токен или повторить запрос. Это сбой API, код 4.

Исходящий HTTP, как и остальные вызовы, ставит `Accept: application/json`, таймаут 30 секунд и user agent `boosty-cli/<version>`. Это не второй заголовок авторизации.

Негодный `BOOSTY_DEVAPI_BASE` остаётся уже существующей локальной ошибкой клиента, код 5, без запроса. Срез этот код не переназначает.

## Разбор

Ответ разбирается как JSON, даже если content type нет. Неизвестные поля игнорируются. Нет `users` или `subscriptions`, нет обязательного поля внутри их объектов, или поле не того типа — ошибка, DevAPI повторно не вызывается. Отсутствие `extra.nextOffset` к этой ошибке не относится. Приведения типов нет: строка вместо числа или логического значения не становится числом, число вместо строки не становится `payments`.

Обязательны оба массива: `users` и `subscriptions`. Пустой массив — успех, не отсутствие поля. `null` вместо массива — ошибка типа.

Объект в `users`, обязательные имена без добавления и без переименования: `id`, `name`, `email`, `avatarUrl`, `flags`. Во `flags` — `isAuthor` и `isBanned`. `id` — целое `i64`, не `i32`. `name`, `email` и `avatarUrl` — строки. Оба флага — JSON-логические значения.

Объект в `subscriptions`: `id`, `ownerId`, `levelId`, `startTime`, `endTime`, `nextPayTime`, `subscriberId`, `payments`. Все id и timestamps — `i64`, не `i32`. `payments` — строка.

`endTime` и `nextPayTime`, равные `0`, — обычные целые, не ошибка разбора. То же для нуля в `startTime`. Ноль не становится JSON `null` и не становится `1970-01-01`.

`extra.nextOffset`, если он есть в ответе, — целое `i64`, не `i32` и не строка. Значение не пересчитывается. Отсутствие `extra` или отсутствие `nextOffset` не ошибка отсутствующего обязательного поля: задача и `AGENTS.md` требуют печатать курсор только когда поле есть и не считать отсутствие концом списка. Команда не добавляет `extra` или `nextOffset`, которых в ответе не было. Если поле есть, но оно не целое, это ошибка типа, код 4, и курсор не выдумывается.

Строки не выкидываются и не склеиваются. Пользователь без подписки остаётся. Подписка, чей `subscriberId` нет среди `users`, тоже остаётся. Срез не синтезирует связь, которой формат не задаёт.

Неуспех HTTP, обрыв, таймаут, не-JSON и отсутствие обязательного поля — код 4. Stdout пуст. Тело ответа в stderr, логи, `Display` и `Debug` не попадает. Ключ и email не попадают в логи, `Display` и `Debug`.

## Курсор

`extra.nextOffset` прокидывается без изменения. Это не `offset + limit` и не длина страницы. Сравнение с посланным `offset` и с числом строк ничего не меняет: строка печатается, JSON сохраняет число, второй запрос не уходит.

Если поле есть, человеческий stdout содержит строку `следующее смещение: N`. `N` — десятичная запись того же целого, без разделителей разрядов и без подмены. Ноль здесь не timestamp: это `следующее смещение: 0`, не «нет» и не `null`.

Если поля нет, этой строки нет. Команда не печатает конец списка и не оставляет из-за этого пустой stdout, когда остальной ответ годен. Это запрет признака конца списка, а не подписи timestamp: слово в подписи времени само по себе концом списка не считается. Короткая страница и `nextOffset`, равный посланному `offset`, тоже не конец списка.

## Вывод

Успех — код 0. На успехе stderr пуст.

С `--json` stdout — тело ответа с именами полей спеки, один JSON-объект, без второй строки и без логов. Неизвестного поля из ответа в нём нет. Порядка ключей нет в контракте. `payments` — та же строка, что в ответе. Ноль timestamp остаётся целым `0`. Если в ответе был `extra.nextOffset`, в stdout то же целое, не строка и не `null`. Если поля не было, в stdout его нет. Пустые массивы остаются пустыми массивами. Email в этом объекте есть, потому что это поле ответа.

Без `--json` stdout — русский текст, не дамп JSON и не колонка сырых имён полей. Строки группируются. У пользователя имя раньше id. Email из ответа печатается, не скрывается. Флаги показаны русскими словами, не ключами `isAuthor` и `isBanned`. Конкретные русские подписи сверх `следующее смещение: N` и «нет» не фиксируются.

`payments` в модели и в `--json` остаётся строкой. В человеческом виде она не разбирается как число и не переставляется как `price`: у этого ответа поля `price` нет. Ненулевой timestamp — локальные дата и время. Ноль timestamp — слово «нет», не `1970-01-01`, не JSON `null` и не дефис. Это относится к `startTime`, `endTime` и `nextPayTime`. Правило не переписывает срок сессии в выводе auth и не меняет уже обещанный вид `user`, `subscription-levels` и `subscriptions`.

Пустой список — успех, код 0. Это не ошибка и не повод оставить stdout пустым: пустой stdout значит ошибку.

Email есть в stdout успешной команды и отсутствует в stderr, логах, `Display` и `Debug`. Ключ, токены и секреты не попадают ни в один поток и ни в логи.

На любой ошибке stdout пуст. С `--json` на stderr ровно один объект `{"error","kind"}`. Текст `error` английский. `kind` — ровно одно из `usage`, `auth`, `api`, `io`. Без `--json` на stderr короткое русское сообщение.

Коды:

- `0` — успех, включая пустые списки, отсутствие `nextOffset` и страницу, которая не длиннее `limit`
- `2` — usage
- `3` — нет или пустой `BOOSTY_API_KEY`
- `4` — сбой, неуспешный HTTP или негодное тело DevAPI
- `5` — негодный базовый URL, как у существующего клиента

Соответствие `kind`: `usage` — 2, `auth` — 3, `api` — 4, `io` — 5.

## Проверки

Тесты ходят только на локальный сервер через уже существующую подмену базы. Boosty не вызывается. `BOOSTY_API_KEY`, `BOOSTY_CLIENT_SECRET` и файл токенов разработчика из окружения не читаются. Свои фейковые значения тесты задают сами. Фикстура лежит в `tests/fixtures/`. Значения фейковые и не скопированы из примеров контракта. Образец ключа из `devapi.md` в фикстуру, код и этот файл не попадает.

- Разбор фикстуры с `users`, `subscriptions` и `extra.nextOffset`: обязательные поля на месте, неизвестное поле отброшено, хотя бы один id вне диапазона `i32` остаётся `i64`, `payments` остаётся строкой, `endTime` и `nextPayTime`, равные `0`, остаются `i64` и не становятся ошибкой или `null`. `nextOffset` вне диапазона `i32` остаётся `i64` и не равен `offset + limit`. Нет `users` или `subscriptions`, либо поле не того типа — ошибка. Пустые оба массива разбираются успешно. Ответ без `extra.nextOffset` разбирается успешно и не получает выдуманный курсор. `nextOffset` строкой — ошибка типа.
- Локальный HTTP: один `GET`, путь `/v1/subscribers`, в пути нет блога. Query ровно из переданных флагов. Без флагов нет `is_free`, `limit` и `offset`. `--is-free true` даёт `is_free=true`, `--is-free false` даёт `is_free=false`, `--limit` и `--offset` дают свои целые, включая переданный `0`. Лишних параметров нет. Ровно один заголовок `X-Api-Key`, значение — фейковый ключ теста, без схемы. `Authorization` нет, Bearer нет, Basic нет, даже если тесту заданы свой файл токенов и свой клиентский секрет. `Accept: application/json` и user agent `boosty-cli/<version>` есть. Второго запроса нет, в том числе когда ответ содержит `nextOffset`.
- Отдельная проверка без флага `--is-free`: параметра `is_free` нет и при отсутствии остальных флагов, и когда заданы только `--limit` и `--offset`.
- Нет или пустой `BOOSTY_API_KEY`: код 3, сеть молчит, stdout пуст, даже если файл токенов на месте. Bearer не ушёл. Token endpoint не вызывался. Файл токенов не переписан.
- `--json` до и после подкоманды. Stdout парсится как один JSON-объект с именами полей спеки, без лишнего поля фикстуры и без второй строки. `extra.nextOffset` равен целому из ответа, не `offset + limit`, в том числе когда он равен посланному `offset` и когда страница короче `limit`. Если поля в ответе не было, в stdout его нет. `payments` посимвольно равен ответу. Ноль timestamp остаётся целым `0`. Ключа в stdout и stderr нет.
- Человеческий stdout, когда поле есть: строка `следующее смещение: N` с тем же `N`, включая `0` и значение, равное посланному `offset`. Это не JSON. Имя пользователя раньше его id. Email есть. Ключей `isAuthor` и `isBanned` нет. Ноль timestamp показан как «нет», без `1970-01-01`. Ненулевой timestamp при фиксированной временной зоне — локальные дата и время. `payments` не переставлен как валюта.
- Когда поля нет: строки `следующее смещение` нет, конец списка не напечатан, код 0, stdout не пуст, если остальное тело годно, запрос один. Короткая страница и `nextOffset`, равный посланному `offset`, тоже не глушат вывод и не вызывают второй запрос.
- Email есть в человеческом и JSON stdout и отсутствует в stderr, логах, `Display` и `Debug`.
- Ошибка DevAPI и тело без обязательного массива: stdout пуст, код 4, второго запроса нет, Bearer не подставлен. С `--json` stderr парсится как `{"error","kind"}`.
- Лишний позиционный аргумент, флаг блога, значение `--is-free` не из `true|false` или нецелый `--limit` или `--offset` — usage, код 2, сеть молчит.
- Пустой список: код 0, stdout не пуст. С `--json` это тело с пустыми массивами, не объект ошибки.
- Help на русском и это не английский шаблон clap.
- Уже обещанные `subscription-levels` и `subscriptions` не начинают принимать `is_free` и не печатают `следующее смещение`. Срок в выводе auth не меняется из-за правила «нет» для нулевого timestamp этой команды.
