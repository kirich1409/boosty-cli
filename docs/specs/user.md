# Команда user

Срез добавляет `boosty user`: один вызов `GET /v1/user` от имени пользователя. Провод ответа остаётся в `devapi.md`. Контракт refresh остаётся в `authorization_code_flow.md` и `docs/specs/auth.md`. Этот файл их не копирует и не меняет. Примерные секреты, ключи, токены и адреса из контракта сюда не переносятся и в код, тесты и фикстуры не копируются.

Каркас уже есть: `auth login`, `auth refresh`, `auth status`, клиент, вывод и конфиг. Срез их не заменяет и второй каркас не строит. Команда не собирает URL и не ставит заголовок авторизации сама: это делает клиент. Refresh — уже существующий, не второй.

Закрытые решения из тела задачи и `AGENTS.md` не переоткрываются. Пример `X-Api-Key` в `devapi.md` для `/v1/user` не является вторым режимом.

## Не входит

- `subscription-levels`, `subscriptions`, `subscribers` и любой другой метод DevAPI.
- Имя или id блога, query, пагинация, второй запрос к DevAPI, скачивание `avatarUrl`.
- Смена поведения `auth login`, `auth refresh` и `auth status`: authorize, обмен кода, имена `redirect_url` / `redirect_uri`, способ атомарной записи. Срез только вызывает уже существующий refresh и не пишет файл вторым путём.
- Заголовок `X-Api-Key` и `Authorization: Basic` на вызове `/v1/user`. Режимы не подменяются и оба заголовка не отправляются.
- Веб-API Boosty, MCP, library crate, agent skill, pull request и мерж в main.
- Новые флаги, переменные окружения, поля ответа и grant.

## Команда

`boosty user`.

Позиционных аргументов нет. API key, client secret, access token и refresh token не принимаются флагами и позиционными аргументами. Своих флагов у команды нет. Глобальный `--json` принимается и до, и после подкоманды: `boosty --json user` и `boosty user --json`.

Лишний аргумент или неизвестный флаг — usage, код 2. Stdout пуст. С `--json` stderr — один объект `{"error","kind"}` с `kind` равным `usage`, без английского текста clap. Код 2 остаётся у clap.

Справка, описание команды и флагов — русские. Английский шаблон help clap не оставлять.

Один запуск — один запрос к DevAPI, и только если до него дошло. Страницы внутри команды не обходятся.

## Запрос

Метод `GET`. Путь — `/v1/user` у базы DevAPI. База по умолчанию `https://devapi.boosty.to/v1`; в тестах её подменяет уже существующий `BOOSTY_DEVAPI_BASE`. Query нет. Другого пути и другого хоста нет.

Заголовок авторизации ровно один: `Authorization: Bearer`, значение — слово `Bearer`, пробел и access token, которым команда вправе пользоваться. `X-Api-Key` не отправляется, даже если `BOOSTY_API_KEY` задан. `Authorization: Basic` не отправляется.

Bearer отправляется только если `token_type` равен `Bearer`. Другая строка, в том числе другой регистр, Bearer не считается. Тогда заголовок не ставится и DevAPI не вызывается. Это отсутствие требуемых учётных данных, код 3. Файл токенов из-за этого не переписывается. Вне окна refresh token endpoint тоже не вызывается.

Исходящий HTTP, как и остальные вызовы, ставит `Accept: application/json`, таймаут 30 секунд и user agent `boosty-cli/<version>`. Это не второй заголовок авторизации.

Ответ разбирается как JSON, даже если content type нет. Неизвестные поля игнорируются. Нет поля, которое формат ответа в `devapi.md` задаёт для `/v1/user`, или оно не того типа — ошибка, DevAPI повторно не вызывается. Обязательные имена, без добавления и без переименования: объект `user`; в нём `id`, `name`, `email`, `avatarUrl`, `flags`; во `flags` — `isAuthor` и `isBanned`. `id` — целое `i64`, не `i32`. `name`, `email` и `avatarUrl` — строки. Оба флага — JSON-логические значения. Строка вместо числа или логического значения не подменяется.

Неуспех HTTP, обрыв, таймаут, не-JSON и отсутствие обязательного поля — код 4. Это не повод для второго refresh и не повод повторить GET. Stdout пуст. Тело ответа в stderr, логи, `Display` и `Debug` не попадает.

## Окно refresh

Access token обновляется перед вызовом, если до `expires_at` не больше 60 секунд. Сравнение в целых unix-секундах, той же единицей, что `expires_at`: refresh нужен, когда `expires_at <= now + 60`. Ровно 60 секунд — внутри окна. Уже истёкший токен — внутри окна. Больше 60 секунд — снаружи: token endpoint не вызывается, файл токенов не меняется, клиентские учётные данные для этого запуска не нужны.

Внутри окна выполняется тот же refresh, что `boosty auth refresh`, включая ротацию refresh token и атомарную запись. Второй реализации refresh нет. Успешный ответ refresh сначала атомарно записывается во временный файл и rename, и только потом отправляется `GET /v1/user`. В Bearer уходит новый access token. Прежний refresh token после успешного ответа refresh в файле не остаётся.

Неуспешный refresh DevAPI не вызывает и прежний файл не меняет. Коды этого refresh срез не переназначает: отказ token endpoint с HTTP 4xx и отсутствие учётных данных — код 3, как требует задача и как уже делает `auth refresh`; обрыв, не-JSON или ответ token endpoint без обязательного поля — код 4; ошибка записи — код 5. Иначе срез изменил бы auth flow.

Если refresh успел записать новый файл, а `GET /v1/user` затем упал, файл не откатывается: откат вернул бы уже недействительный refresh token. Если после успешной записи `token_type` не `Bearer`, DevAPI не вызывается, код 3, новая запись остаётся.

## Нет токена

Нет файла токенов — код 3, ни DevAPI, ни token endpoint.

Файл не читается или в нём нет обязательного поля — код 5, как у чтения файла токенов сейчас. Сеть не вызывается, файл не переписывается.

## Вывод

Успех — код 0.

С `--json` stdout — тело ответа с именами полей спеки, один JSON-объект, без второй строки и без логов. Неизвестного поля из ответа в нём нет. Порядка ключей нет в контракте. Числовые значения не становятся `null`. Email в этом объекте есть, потому что это поле ответа.

Без `--json` stdout — русский текст, не дамп JSON и не колонка сырых имён полей. Имя раньше id. Email из ответа печатается, не скрывается. Флаги сгруппированы с пользователем и показаны русскими словами, не ключами `isAuthor` и `isBanned`. Конкретные русские подписи сверх этого не фиксируются. `avatarUrl` не запрашивается отдельным HTTP-вызовом.

Email есть в stdout успешной команды и отсутствует в stderr, логах, `Display` и `Debug`. Access token, refresh token, секрет и authorization code не попадают ни в один поток и ни в логи.

На успехе stderr пуст.

При любой ошибке stdout пуст. С `--json` на stderr ровно один объект `{"error","kind"}`. Текст `error` английский. `kind` — ровно одно из `usage`, `auth`, `api`, `io`. Без `--json` на stderr короткое русское сообщение. Секреты и токены не печатаются.

Коды:

- `0` — успех
- `2` — usage
- `3` — нет файла токенов, нет Bearer-учётных данных, `token_type` не `Bearer`, отказ refresh, который существующий refresh уже считает auth
- `4` — сбой или негодное тело DevAPI, а также транспортная или разборная ошибка refresh, которую существующий refresh уже считает api
- `5` — нечитаемый файл токенов, нет обязательного поля файла, ошибка записи refresh

## Проверки

Тесты ходят только на локальный сервер через уже существующие подмены базы. Boosty не вызывается. `BOOSTY_API_KEY`, `BOOSTY_CLIENT_SECRET` и файл токенов разработчика из окружения не читаются. Фикстура лежит в `tests/fixtures/`, значения фейковые и не скопированы из примеров контракта.

- Разбор фикстуры user: обязательные поля на месте, неизвестное поле отброшено, `id` вне диапазона `i32` остаётся `i64`. Нет обязательного поля или тип не тот — ошибка.
- Локальный HTTP: ушёл один `GET` с путём `/v1/user` и без query. Ровно один заголовок `Authorization: Bearer`. `X-Api-Key` нет, даже если тесту задан свой фейковый `BOOSTY_API_KEY`. `Authorization: Basic` нет. `Accept: application/json` и user agent `boosty-cli/<version>` есть. В Bearer — тот access token, которым команда вправе пользоваться после окна refresh, не прежний, если refresh был.
- Граница 60 секунд на фиксированных часах: оставшаяся секунда 60 и уже истёкший токен вызывают refresh; 61 секунда и больше — нет, token endpoint молчит, файл не меняется, вызов user при этом успешен и без клиентского секрета.
- Успешный refresh внутри окна: в файле новый refresh token до запроса DevAPI и до текста успеха; запись атомарная. Неуспешный refresh (отказ 4xx) — код 3, байты файла прежние, DevAPI не вызывался. Неудачный rename — код 5, байты прежние, DevAPI не вызывался.
- Нет файла токенов — код 3, сеть молчит, stdout пуст.
- `token_type` не `Bearer` вне окна — код 3, DevAPI и token endpoint молчат.
- `--json`: stdout парсится как один JSON-объект с именами полей спеки, без лишнего поля фикстуры и без второй строки. Имя, email и id в нём равны ответу. Токена в stdout и stderr нет.
- Человеческий stdout: имя раньше id, email присутствует, это не JSON и не ключи `isAuthor` / `isBanned`. Email нет в stderr.
- Ошибка, включая ответ DevAPI без обязательного поля и HTTP-ошибку DevAPI: stdout пуст, код 4 для этой пары, файл не откатывается, если refresh уже успешно записан. С `--json` stderr парсится как `{"error","kind"}`.
